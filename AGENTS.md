# AGENTS.md

This file provides guidance to AI coding agents (ZCode, Claude Code, etc.) when working with code in this repository.

## Project Overview

NEU-Ecode: a minimal Android app (Kotlin, single `:app` module, package `com.neboer.ecode`) that logs into Northeastern University's (东北大学) CAS single sign-on and displays the student's E码通/一码通 QR code. There is no official API — everything is screen-scraping of the university's web endpoints, so the login flow is inherently fragile.

## Build Commands

Gradle 8.5 wrapper, AGP 8.2.2, Kotlin 1.9.22, JDK 17 (compileSdk 34, minSdk 24). There are **no test sources or test dependencies** in the repo.

- `./gradlew assembleDebug` — build debug APK
- `./gradlew installDebug` — build and install to a connected device/emulator
- `./gradlew lint` — Android lint
- `./gradlew :app:compileDebugKotlin` — fast compile check

There are no tests to run. Verification is build + install on a device; the login flow can only be exercised with a real NEU student account.

## Versioning + Releases

- `versionName`/`versionCode` are derived from git tags in `app/build.gradle.kts` (top of file): tag pushes (`v1.2.3`) use `GITHUB_REF_NAME` directly, local builds use `git describe --tags --match v*`, falling back to `1.0.0` when no tag exists. `versionCode` = major\*10000 + minor\*100 + patch. The in-app version label (`SettingsActivity`) reads `PackageInfo.versionName`, so it follows automatically — never hardcode versions
- `.github/workflows/build-apk.yml` builds a signed release APK on `v*` tag pushes (attaches it to a GitHub Release) and on manual `workflow_dispatch`. Signing reads env vars `SIGNING_STORE_FILE`/`SIGNING_STORE_PASSWORD`/`SIGNING_KEY_ALIAS`/`SIGNING_KEY_PASSWORD`, wired from GitHub Secrets (`KEYSTORE_BASE64` + the three passwords); without them the workflow still builds but the APK is unsigned/not installable. The keystore is the user's own file at `C:\Users\zhx\AndroidKeys\e-one` (alias/password held by the user, never committed); its base64 copy lives in `keystore/` (gitignored) for pasting into Secrets — see `keystore/signing-info.txt`
- To release: commit, tag `vX.Y.Z`, push the tag — that's the whole loop

## Architecture

Plain Activities with hand-rolled OkHttp networking — no DI, ViewModel, or Repository layers; classes are constructed inline with the Activity as context. All classes live flat in `app/src/main/java/com/neboer/ecode/`.

### Activities

- `MainActivity` (launcher) — the home screen doubles as the entry point; it is always reachable, even logged out. On `onCreate`/`onResume` it checks `WebViewCookieJar.hasEcodeSession()` (the ecode API's HttpOnly `SESSION` cookie in the WebView CookieManager — see "Credential model"): logged in → QR + balance data flow; logged out → empty state ("未登录" placeholder with a 去登录 button that opens `LoginActivity`; settings also hosts a 登录 entry). Session changes are picked up on `onResume` by re-checking the cookie, so login completion / account switch needs no result plumbing. When the QR session dies (`AuthExpired`) it first tries a native silent re-login from the stored credentials (`runSilentRelogin` → `SilentRelogin`, see item 7 below); if that is unavailable, or comes back "successful" without a fresh code, it falls back to the empty state through `degradeQrSession()` — which clears **only** the ecode cookies (`clearEcodeSession()`), keeping `CASTGC` and the portal pair alive so a dead QR session doesn't force a full re-login for balance. **两个细节别改坏**:(a) `silentReloginUnhelpful` 必须与 `SilentLogin.decide()` **并列**判断 —— `record(Success)` 只写 60s 冷却,冷却一过 ALLOW 就会回来,把这个守卫放进 decide() 的非 ALLOW 分支等于没写,那个冷却一过就会重新开始"成功但没用"的循环;(b) `runSilentRelogin()` 返回 **Boolean**(true = 这一发归它收场),返回 false 时**不会有任何回调到来**,所以调用方不能就此结束自己的循环 —— 二维码那条路是等 `SILENT_RELOGIN_WAIT_MS`(3s)再拉一次码,因为那一发可能由余额那条路发起、成功后只重查余额,直接 `return@launch` 会让二维码停更直到下一次 `onResume`;余额那条路则退回"¥ --"而不是停在"加载中"等一个不会来的回调。等待本身有界:静默重登的 HTTP 超时是 15–20s,且任何结局都会 `record()` 记账(冷却/熔断随即挡住下一轮)。 **静默续期失败时会把人送到登录页**:`NeedSecondFactor` → 打开登录页的二次验证面板,`Rejected` → 打开登录页并清空密码框(见 item 7)。这是"登录与自动续期是一件事"的落点——两条路只有"有没有人在旁边填验证码"这一个区别
- `LoginActivity` — **2026-09-14 起是应用自有表单,不再套 WebView**。同一页三个面板(`showOnly()` 切换):账密表单 / 二次验证 / 加载失败。取表单 `fetchLoginForm()`,提交 `submitCredentials()`,二验 `fetchCaptcha()` + `requestSmsCode()` + `submitSecondFactor()`;成功判据与静默续期**完全相同** —— `CasStep.Ticket` 的 Location 交给 `consumeTicket(location, verify)` 消费掉再真校验(`qr-code` 200),**不看本地 cookie 在不在**。要点:(a) `lt`/`execution` 一次性,账密被拒后旧表单作废,必须 `loadLoginForm(afterError=…)` 重新取一张才能再提交;(b) 二验被拒时服务端**返回一张新表单**(token 已换),要整体换掉再刷新图形码,拿旧的重复提交会一直被拒;(c) 短信只在"获取短信验证码"按钮里发(`requestSmsCode` 是全应用唯一入口);(d) 账密在**服务端接受之后**才暂存(`pendingUsername`/`pendingPassword`),真正落盘要等 `onLoggedIn()` 里的 `applyCredentialChoice()`——点登录就存会把打错的密码存进去,随后静默续期连试两次不中直接熔断;(e) `loadLoginForm()` 开头 `if (busy) return`,所以调用它的失败分支必须先 `setBusy(false)`,否则界面卡在进度条上不动(这个坑踩过一次);同理 `btnRestartLogin`/`btnRetry` 这两颗"只重取一张表单"的按钮也归 `setBusy()` 管(busy 时不关掉,点下去就是毫无反应),而 busy 跳过本身会记一条 `Log.w` 留痕;(f) **兑票失败绝不能退回 `loadLoginForm`**:TGT 还活着时它会再给出 `Redirected`,于是"兑票失败 → 重取表单 → 又 Redirected → 再兑票"成为无人按动的死循环,所以那条路走错误面板(它的"重试"与底部常驻的网页登录就是出路);(g) 二验 `mode` 的兜底是 **unknown 不是 mobile**:服务端换了按钮 id 时猜成 mobile 会给出一个"看着能用却永远发不出码"的短信面板,unknown 才会落到"不支持"面板(那里有网页登录逃生口)。所有 `IOException` 在 Activity 内就地转成文案,不让它穿透。**它还是全应用唯一的凭据录入处**:勾选框"保存账号密码,自动续期"就是自动续期的开关(勾选=存,取消=清,都只在登录成功后执行),设置页不再单独提供录入对话框。三种进入方式:`applyInitialState()` 按 Intent 分派 —— 普通进入 / `EXTRA_SECOND_FACTOR`(静默续期交来的二验表单,**直接落到二验面板**)/ `EXTRA_INVALID_PASSWORD`(账号预填、密码清空、说明原因)。页面底部常驻 `btnWebLogin`(网页登录)不随面板切换
- `WebLoginActivity` — **逃生口**,不是默认路径:真 WebView 包着 CAS 登录页,`activity_web_login.xml` + `prefillJs` 预填。两个入口:登录页底部**常驻**的"网页登录(兼容模式)"按钮,以及学校要求的验证方式原生做不了(`mode` 既不是 `mobile` 也不是 `email`,如微信扫码)时由 `showSecondFactor` 引导过来的错误面板。留它的理由:整个应用是屏幕抓取,校方改版可能让原生解析整个失灵,而"登录"是唯一不能失灵的功能。它的判成功方式与原生路径**同源**,但多两道便宜的预筛:先要求 WebView **本次真的落到过 ecode** 且 ecode 的 `SESSION` 已落地(否则连登录页都还没提交,没什么可校验的),再打一发 `qr-code` 真校验(`EcodeApiClient.hasAuthenticatedSession()`,与原生路径那条完全相同);两次真校验之间隔 `VERIFY_MIN_INTERVAL_MS`(3s),否则"落在 ecode 主机上但会话未被确认"这个稳态(比如那张票无效、服务端回 500)会变成每 800ms 一发 qr-code 的连环请求。**光有预筛不够**:`SESSION` 是约 100 d 的持久 cookie,而一张无效的票也能落到 ecode 主机上,那时"到过 ecode + 本地有 SESSION"就会自报成功 —— 无限闪屏就是这么来的。预筛里"到过 ecode"的判定**必须**是解析主机名的 `isEcodeUrl`;那个"顺手的" `url.contains("ecode.neu.edu.cn")` 对本页加载的 CAS URL 恒真(它的 `service=` 参数只把 `:` 和 `/` 百分号转义,主机名原样保留)
- `SettingsActivity` — 账号卡片一张卡管两件事:**登录状态**与**自动续期状态**(`renderAccountState()`),**只有状态、没有开关**:自动续期在实现上就是"登录时勾选了保存账号密码",开关就是登录页那个勾选框,再放一个"开启/关闭自动续期"按钮等于给同一件事开两个入口(而且那个入口在"本地 TGT 还活着"时根本走不到输入账密那一步,按下去看着就是坏的)。唯一动作按钮是 `btnSwitchAccount`(`confirmAccountAction()`):已登录 → **二次确认弹窗** → `clearAll()` + `CredentialStore.clear()`,未登录 → 直接进登录页。**切换账号是全应用唯一会"清除所有"的动作**(会话 + 已存账密),所以它同时就是"关闭自动续期"和"换个人"的出口。未登录但开着自动续期时,状态行会补一句 `autoRenewFailureReason()`(取自 `SilentLogin.lastOutcome()`:需要验证码 / 密码已失效)。另有 QR brightness mode dropdown (FULL default / HDR experimental / SYSTEM)、开屏二维码显示 dropdown (`qrShowOnLaunch`)、返回方式 radio buttons;the 关于 section hosts the online-update state machine (see below)

### QR + balance refresh model

- The QR loop runs **only while foregrounded AND the QR card is visible**: `onPause` cancels the loop job, re-showing the card or returning to the foreground restarts it (fresh fetch immediately). Tapping the card toggles visibility for the current session only (not persisted); each launch starts from `AppSettings.qrShowOnLaunch`. Hiding the card cancels the loop; tapping it again restarts
- QR highlight (`AppSettings.qrBrightnessMode`, default FULL): FULL = window brightness forced to 1.0 while showing the QR (traditional); HDR (experimental, needs API 34+ and an HDR-capable screen, checked by `HdrHelper.isHdrSupported`) = window switches to `COLOR_MODE_HDR` at system brightness while `HdrHelper.attachGainmap` mounts an Ultra HDR gainmap on the QR bitmap (white modules gain, black stay SDR) so only the QR hits peak brightness — unsupported devices silently fall back to FULL; SYSTEM = no brightness override. Changing the setting takes effect on `onResume` (bitmap regenerated to mount/unmount the gainmap)
- Refresh cadence is driven by the server: `EcodeApiClient` parses `data[0].attributes.qrInvalidTime` (unix seconds) and the loop schedules the next fetch at expiry +500 ms (clamped 1 s–120 s; falls back to 10 s when the field is missing)
- `EcodeApiClient.fetchQRCode()` returns a sealed `QrFetchResult`: `Success(qrCode, invalidAtMs)` / `AuthExpired` (CASTGC renewal failed → main screen clears the session, shows the empty state with "登录已过期") / `NetworkError` (IOException → exponential backoff retry 5 s→30 s; never clears the session). Catching IOException here is what keeps a dead network from crashing the coroutine
- Balance: `PortalClient.fetchBalance()` returns a sealed `BalanceResult` (`Success`/`NetworkUnreachable`/`SessionExpired`/`Failed`). Balance loads once automatically per session (on login return) and afterwards only manually. `SessionExpired` is separate from `Failed` so the UI says "重新登录后才能查询余额" instead of "稍后重试"

### CAS/CASTGC session lifetime (2026-09 captures — read this before touching auth)

Measured from the `.har/` captures, not assumed:

- `CASTGC` is the TGT cookie and the **only** way to mint a ticket silently. It is issued **only** by a real credential login (`pass.neu.edu.cn` POST), with `Max-Age=7200` (**2 hours**, `Path=/tpass/`, not HttpOnly). Ticket validation does **not** re-issue or refresh it: in `.har/ecardlogin.har` a silent SSO (`CASTGC` in → 302 with `ST-…` out) returns only `Language` in `Set-Cookie`. A dead TGT shows up as tpass answering **200 with the login HTML** instead of a 302 with a ticket
- When the second factor IS demanded, the credential POST answers **200 with the same page in 2FA state** (not a ticket, not a redirect), and the rest is a three-step dance — the whole request sequence is in `.har/webvpn.neu.edu.cn.har` (2026-09-10), and the client-side contract in `.har/_js2/login_second.js` (fetched live from the server: it is a static asset needing no auth, so it is recoverable any time — the HAR itself kept only response *metadata* for this flow, its bodies having been stripped on export): (1) `GET /tpass/code?<random>` renders the image captcha into `#codeImage`; (2) `POST /tpass/secondAuthCode` with form body `code=<captcha>&method=mobile` is **the only thing that sends the SMS** (a POST with `code` — an earlier note here said GET with `imgCode`, which was wrong) and answers JSON `{"success":bool,"message":"…"}`; on `success:false` the page shows `message` and refreshes the captcha; (3) `POST /tpass/login?service=…` with `imgCode=<captcha>&scendAuthCode=<SMS>&method=mobile&RelayState=…&execution=…&_eventId=submit` — the captured instance was `RelayState=e1s2&execution=e1s2` (password step was `e1s1`; the `e2` in that earlier note was also wrong) — answers 302 with `ticket=ST-…`. The page's own JS just does `#second_auth_form[0].submit()`, so a native client need not know the field list defensively: **replay every hidden input of that form verbatim**, overriding only `imgCode`/`scendAuthCode`/`method`/`_eventId`. Detection needs no rendering: on the **login** page `second_auth_form`, `scendAuthCode`, `imgCode` and `#errormsghide` occur **0 times** (only the inert `password_template`/`mobile_template` blocks do — byte-counted on `.har/_fixture/page_raw.html`), so "response HTML contains `second_auth_form`" ⇒ 2FA while "contains `#loginForm` + an error" ⇒ wrong password. Modes are `mobile` / `email` / WeChat-QR, chosen by the `secondMode` param → `secondType` cookie → whichever `#secondAuthBy*` button the server rendered, and this page surfaces errors through `#errormsghide` (the login page has no such element). **Remaining gap:** the 2FA page HTML itself (18555 bytes in that HAR, body not stored) is the one artifact worth capturing; with the replay-everything strategy it is a regression check, not a blocker
- "Remember me" on the CAS page is a **username-only** feature: the `#rememberName` checkbox ("记住账号") writes `neu_cas_un` (365 d) from `login_neu.js` and refills `#un` on load. **No password is ever stored** client- or server-side — submission is `rsa = RSA(username+password)` against a public key hard-coded in the page, with `ul`/`pl` as the plaintext lengths. A `信任此设备` checkbox (`#saveDevice`) exists but only in the login page's SMS-login template (`#template_phone`). Whether the second-auth page offers the same box is now settled: `.har/_js2/login_second.js` renders its `mobile_template`/`email_template` with nothing but a captcha input, an SMS-code input, a 获取验证码 button, a submit button and 返回登录 — no `saveDevice`, and no call to `/tpass/device` anywhere in it, so the web 2FA path has no device-trust control. Conclusion: there is no remembered credential to replay, and no trust token in the cookie set (across six captures pass.neu.edu.cn only ever sets `CASTGC`/`JSESSIONID`/`Language`/`neu_cas_un`/`up_feedback`)
- The second factor is triggered by the **network**, and nothing else. The 2026-09-10 campus login log shows the same Android client twice, differing only in IP: mobile-carrier `223.104.x.x` (off-campus) got the SMS step, campus `172.29.26.65` did not. Platform/browser are not the discriminator, so spoofing a desktop UA does not avoid the SMS. (An earlier reading of `remenberme(personal.neu.edu.cn.har` as a time-based suppression window is superseded — most of those desktop "logins" were silent SSO reuse, which produces no authentication event at all; the one real password-only login there has an unknown network.)
- **Correction (2026-09-14, field observation — not a capture): "every login needs SMS" is wrong.** Off-campus, the *second* password login does not ask for the SMS step, and clearing cookies does not bring it back. So the trigger is neither per-attempt nor cookie-based; the working hypothesis is a **server-side, per-IP (±account) memo with a time window** — once a second factor has been passed from an IP, password-only logins from it are let through for a while. That also explains why it *looked* like a hard requirement: the app only ever logged in after the memo had lapsed (typically the day's first login), so it only ever saw the un-memoized case. This is what makes stored-credential silent re-login viable — see [SilentLogin]. Confirming the window needs a time-series run (login hourly from one IP after one 2FA, log when the SMS step reappears). **Second field observation (same day, user report): a *different* account logging in from the same device also skipped the SMS step** — which narrows the memo to the **IP (not IP+account)**, and is why the native 2FA panel could not be exercised on-device the day it was written. Consequence for testing: any 2FA work must be planned around this window, not against it.
- **The credential POST is entirely built by the login page's own JS** (`.har/logout.har` carries the page's HTML and all 10 of its scripts). `#loginForm`'s visible markup holds `#un`/`#pd` plus hidden `#rsa`/`#ul`/`#pl`/`#lt`/`execution`/`_eventId`/`t_un`/`t_pd`/`t_c` (the `id`s of the last three are actually `r_t_un`/`r_t_pd`/`r_t_c`; only the `name`s are `t_*`); clicking 登录 calls `login()` (`login_neu.js:64-96`), which sets `#ul`/`#pl` to the plaintext lengths, computes `rsa` via **jsencrypt** (`comm/neu/js/rsa.js`) against a 2048-bit public key **hard-coded in `login_neu.js`**, then does `#loginForm[0].submit()`. `login()` also sets **`disabled` on `#un`/`#pd` before submitting**, so the plaintext credentials never appear in the POST body at all — only `rsa` carries them. Consequences for any automation: (a) the submit control is `<input type="button" id="index_login_btn">` — **not** a submit button, and its click handler is bound in `body.onload`; (b) `form.submit()` bypasses all of it and posts an **empty `rsa`**, so any injection must call the global `login()` (function declarations hoist, so it is callable before `onload`); (c) the page ships two copies of the login markup — a real rendered form and an inert `<script type="text/html" id="password_template">` — so selectors must be visibility-aware, and `offsetParent` is the wrong test (`null` for `position:fixed`); use `offsetWidth`/`getClientRects`
- **What a wrong password looks like** (`.har/errorlogin.har`, 2026-09-14 — the bodies are stripped on export, so this capture is status/headers/byte-count only): the credential POST answers **HTTP 200 with `text/html` and no `Location`** — i.e. it re-renders the login page, identical in shape to a successful render, with `Set-Cookie: Language` as the only cookie. There is **no** error status, no redirect carrying an error param, no JSON. So "wrong password" is detectable only from the body: 200 + `#loginForm` still present ⇒ `CasStep.BadCredentials`. Two things follow for the error *text*: the supplied POST body listed only **`rsa`/`ul`/`pl`/`lt`/`execution`/`_eventId`** (the three `t_*` inputs were **not** submitted by the browser that time — our client still sends them as empty strings, which the server ignores; the on-device 10/10 run was with them, so leave it alone rather than "fixing" it towards byte-identity), and `#errormsg` **cannot** be read naively: on the clean page it already contains a `display:none` placeholder 「账号不存在！」, while the real message is rendered server-side into **`#errormsghide`** and only copied into the visible `#errormsg` by the page's own JS (`login_neu.js:152`: `if($("#errormsghide").text()){ $("#errormsg").text($("#errormsghide").text()).show(); }`). `#errormsghide` occurs **0 times** on the clean page, so its presence is itself a strong "this was rejected" signal. `CasAuthClient.visibleErrorText()` therefore reads `#errormsghide` first and only then a visible `#errormsg`; returning null (generic message) is the correct fallback. **Unverified:** where exactly the server injects that element — no capture in the repo has an error-page body, so this is inferred from the page's own JS, and the fallback chain covers both possible renderings
- The university's login log (IP / OS / browser / request path per authentication) is the cheapest instrument for auth work — check it before theorising. It is what revealed that our OkHttp calls were logged as `browser=unknown` (the hardcoded UA had no `Chrome/…` token) while the WebView's were `Chrome Mobile`; [UserAgent] now unifies both by adopting the system WebView's UA, so the app presents one consistent client
- Device trust is a dead end so far. `POST /tpass/device` (the login page's `#template_phone` popup path — the one carrying 信任此设备, with `d`=Fingerprint2 hash, `i`=its details, `m`=2 send / 3 verify, `s`=trust flag, and a per-user device cap that evicts the oldest) returns **HTTP 500** from CAS for `m=2` alone, even off-campus and direct. The web-flow 2FA page has no trust control at all (`#second_auth_form` carries only `imgCode`/`scendAuthCode`/`method`/`RelayState`/`execution`/`_eventId`), and `phone(murmur_s, details_s)` — the only caller of that endpoint — has no call site in any script reachable from the web login page. Only the official app shows the checkbox, so unless its login page/URL can be inspected, treat this route as closed. (2026-09-14: exhaustive over `logout.har`, which carries all 10 scripts the login page loads — `phone(` appears only in its own definition in `login_neu.js:555`, and the only other `device` caller is `#sendCode`, which posts `{m:'2'}` alone with no fingerprint. The `信任此设备` box and the `二次认证` layer are dead code on the web flow.)
- **Logout chain** (`logout.har`, 2026-09-14): `portal.neu.edu.cn/tp_up/logout` → `pass.neu.edu.cn/tpass/logout` (clears `CASTGC` + `CASPRIVACY`, `Path=/tpass/`) → `pass.neu.edu.cn/portal/logout.jsp` → `ehall`'s `db_portal/infoplus/logout` (clears `CAS_TICKET`/`LOGIN_TOKEN`/`TENANT_TICKET`/`X_CAPTCHA`) and, on the personal-portal path, `GET /portal/manage/common/login/logout/do` → sets `CK_LC=deleted; Max-Age=0` and `CK_VL=deleted; Max-Age=0`. It clears **no trust/device token, because none exists** — the whole cookie inventory across the capture is `CASTGC`/`CASPRIVACY`/`JSESSIONID`/`Language`/`neu_cas_un`/`up_feedback`/`SESS_ID`/`CK_LC`/`CK_VL` (+ ehall's `INGRESSCOOKIE` and friends). So logout is not a lever for avoiding the SMS: it removes state rather than creating a trusted condition. What it is good for: after logout every `tpass/login` load carries only `JSESSIONID`/`Language`/`neu_cas_un`/`up_feedback` (no `CASTGC`), i.e. the post-logout credential POST is a clean first authentication — the same state our silent path is already in, since it only runs once `CASTGC` is dead. Note the app's own 切换账号 only calls `WebViewCookieJar.clearAll()` locally and never hits this endpoint, so server-side `CK_LC`/`CK_VL` survive a local account switch
- Portal balance is authorised by `CK_LC` + `CK_VL` **only** (both `personal.neu.edu.cn`, both HttpOnly+Secure, both session cookies with no `Max-Age`). `SESS_ID` is **not** part of it: a forged `SESS_ID` alongside real `CK_LC`/`CK_VL` still returns the full data, while `SESS_ID` alone yields `e=10013`. `CK_LC`/`CK_VL` are minted **only** by the ticket-consuming hop (`cas_login/1?…&ticket=ST`), and **no endpoint re-issues them** (15 portal endpoints swept; only `msg/index` re-issues `SESS_ID`, with `Max-Age=86400`)
- Portal auth failures are **HTTP 200 with `{"e":10013,"m":"登录信息已失效，请重新登录"}`**, not a 4xx/302 — so never judge portal auth by status code, and never use `msg/index` as a liveness probe: it answers `e=0` even for a credential pair that has been revoked by logout, while `items`/`detail` correctly reject forged *and* revoked pairs. `PortalClient.isCredentialAlive()` therefore probes `items` and checks `e == 0`
- Consequence for the "balance dies after a while" problem: there is **no sliding renewal** for `CK_LC`/`CK_VL`. The only way to obtain a fresh pair is to consume a new ticket, i.e. while `CASTGC` is still alive (≤2 h after a real login); without it the portal SSO entry just 302s back to the CAS login page. `PortalClient.keepSessionAlive()` (on every `MainActivity.onResume` + every 30 min, `PORTAL_KEEPALIVE_INTERVAL_MS`) is therefore useful **only inside that 2 h window**: it detects dead credentials and silently re-mints them. Its `msg/index` ping slides `SESS_ID`'s 24 h window, but since `SESS_ID` does not authorise anything that step is best-effort, not a lifeline. **Open question (unverified):** whether the TTL of the `CK_LC`/`CK_VL` record is coupled to the `SESS_ID` session's sliding window. Evidence against it: a pair stays valid with an unrelated (or absent) `SESS_ID`, and a pair revoked by logout leaves its `SESS_ID` session answering `msg/index`. Settling it needs a time-series run (ping one pair's session, leave another untouched, see which dies first)
- Evidenced but non-obvious: logout (`GET /portal/manage/common/login/logout/do?service=…`) revokes **only the credential pair presented with it** — a second, independently-minted pair keeps working — and it does **not** touch `CASTGC` (a fresh ticket can be minted immediately after). So a portal logout costs nothing that a re-ticket can't restore within the 2 h window

### Credential model: what actually authorises each subsystem (2026-09-10 controlled-variable probes)

Measured by one-variable-at-a-time requests (probe lives in the gitignored `demo/`: `cd demo && ./gradlew runProbe`; sections 【1】–【5】 need no credentials, 【6】/【7】 need `ECODE_CASTGC=<TGT>`):

- **ecode API authorises on the HttpOnly `SESSION` cookie alone** — a Spring Session slot (base64 UUID, `path=/ecode/api`, ≈100 d absolute, and **none** of the 8 swept ecode endpoints ever re-issues it). A forged `SESSION` → 401; `SESSION` missing → 401 even with a valid `XSRF-TOKEN`.
- `XSRF-TOKEN` is **not** a credential and **not** a login marker: the server issues one on demand to *anonymous* clients (a bare 401 from `qr-code` plants a fresh `XSRF-TOKEN`; it is only re-sent when the client did not present it — "缺了就发、带了就不发", not per-response rotation), and `X-XSRF-TOKEN` is not validated at all on these GETs (missing / wrong / mismatched all return 200). Because OkHttp writes `Set-Cookie` from **every** response including 401s, our own failed fetches used to keep re-planting the old login marker — so `hasEcodeSession()` now checks `SESSION`, read via a URL under `/ecode/api` (a cookie's `path` decides which URL can see it).
- ecode's `SESSION` is minted by **any** entry into the CAS client, i.e. `GET /ecode/api/sso/login` — with a bogus ticket (500), with no ticket (302 back to CAS), or with a valid one. A valid ticket does not mint a new cookie: it marks the **same** slot authenticated in place (verified by pre-seeding an anonymous `SESSION` and watching its value stay identical while `qr-code` flips 401 → 200). So "a `SESSION` exists" ≠ logged in.
- Renewal is impossible in both directions: `SESSION` is never re-issued, and `CASTGC` (2 h) is never refreshed by ticket validation. The only recovery is a fresh real login.



### Online update (v<xx.xx.xx> releases)

User-initiated from SettingsActivity ("检查更新" button); a 9-state UI state machine (`UpdateUiState`) drives status text / progress bar / one action button (下载更新 / 暂停 / 继续下载 / 安装更新). Components (all flat in `com.neboer.ecode`):

Version comparison: `parseVersion` regex accepts `v1.2.3` / `1.2.3` / `1.2.3-3-gabc` (local git describe suffix is ignored), missing segments default to 0; `isNewer` compares via `toVersionCode` (major*1e6 + minor*1e3 + patch). Tags not matching the pattern → check fails loudly rather than falsely offering an update. GitHub API rate limit (60/hr per IP) makes the proxy fallbacks matter too
- `ApkUpdateDownloader` — blocking `download(release, listener)` for the caller's IO coroutine. 同样的策略:先直连(5 s 客户端,失败即转镜像),再按 `UpdateChecker.orderedProxies(apkUrl)` 的顺序逐个试 —— **兜底顺序永远是全部镜像的一个排列**,所以"最快的也失败了"不会让其余镜像白等。Every attempt sends `Range: bytes=<part length>-` so any failure (dead proxy mid-stream, user pause, process death) resumes from the `.part` file in `getExternalFilesDir(null)/update/`; HTTP 200 (range ignored) restarts cleanly, 416 deletes the stale `.part`. Completion requires the byte count to reach the Content-Range total, then `.part` renames to `Ecode-<version>.apk`. Progress callbacks are throttled to ~150 ms and posted to the main thread. `cleanupExcept(version)` purges other versions' files after a check. Static helpers `partialFile`/`downloadedApk`/`updateDir` are shared with the Activity
- `ApkInstaller` — FileProvider URI + `ACTION_VIEW` install intent; on API 26+ without "install unknown apps" permission it stores the path in `pendingApkPath` and opens `ACTION_MANAGE_UNKNOWN_APP_SOURCES`; `SettingsActivity.onResume` calls `resumePendingInstall` to continue after the grant

- JVM-verified via the demo harness: `cd demo && ../gradlew runUpdate` runs version-compare assertions plus a real release query (direct-first) / direct-first download / resume-after-truncated-`.part` / `cleanupExcept` / mirror-fallback ordering against GitHub (Android stubs: `Handler`/`Looper`/`getExternalFilesDir` added in `demo/src/main/kotlin/android/`). The harness's copies of `UpdateChecker.kt`/`ApkUpdateDownloader.kt` are **exact mirrors of the app sources** — after editing either in `app/`, copy it over before trusting a run. One gotcha it already tripped on: the **first** `measureLatencies` call in a process pays DNS+TLS (cold) while later ones reuse pooled connections (warm), so two runs of the same measurement are not comparable — don't assert an order from one map against an order produced by a different measurement (that's a false failure, not a bug)

### Auth + QR flow (the core)

1. `LoginActivity`(原生表单,**交互路径**)—— 账密 → 二验 → 兑票,全部由 `CasAuthClient` 在应用内走完,不再有 WebView。成功 = 票被消费掉 **且** `EcodeApiClient.hasAuthenticatedSession()`(qr-code 200)为真;`setResult(RESULT_OK)` + `CLEAR_TOP|SINGLE_TOP` 回 `MainActivity`(设置页随之出栈),主界面 `onResume` 重新判登录态并自动刷一次余额(登录态从 false 变 true 时重置 `balanceAutoLoaded`,否则刚登录完余额还是"未知")。`SESSION` 仍是**唯一**的会话来源,但它由 OkHttp 经 `WebViewCookieJar` 写进 CookieManager,不再是 WebView 种下的;判成功**绝不用**"cookie 在不在"——`SESSION` 是 ~100 d 的持久 cookie,它在与服务端认不认它是两件事,这正是旧版无限闪屏的根因。逃生口见 `WebLoginActivity`
2. `CasAuthClient.establishSession(entryUrl, expectedHost)` (formerly `CasSessionRenewer`, deleted) — 换票通用步骤:GET 入口,valid `CASTGC` 被 302 直送到服务端消费票;`Establish.OK` = 落到期望主机。ecode 用它(`ecode` 入口 + `hasEcodeSession()`),门户用它(自己的 `cas_login/1` 入口 + `personal.neu.edu.cn`)。落到 CAS 自己 = `NO_TGT`(TGT 死了),落到别处 = `ELSEWHERE`(链路变了)。IOException 向上抛,由调用方归类成 `NetworkError`。只在最后 2 h 内有效 —— 见 "CAS/CASTGC session lifetime"
3. `EcodeApiClient` — GET `https://ecode.neu.edu.cn/ecode/api/qr-code`, authorised by the `SESSION` cookie the CookieJar attaches; `X-XSRF-TOKEN` is still sent (re-read from the CookieManager per request) to look like the browser, but it is **not** validated on this GET. QR string at `data[0].attributes.qrCode`, expiry at `data[0].attributes.qrInvalidTime` (unix seconds). First failure → renew → retry once; returns sealed `QrFetchResult` (see "QR + balance refresh model")
4. `AppSettings` — plain SharedPreferences ("ecode_settings"): `backPressMode`, `qrShowOnLaunch`, `updateSourceId`, `qrBrightnessMode`
5. `BalanceSource` / `PortalClient` — balance source abstraction over sealed `BalanceResult`; `PortalClient` (the only implementation) is the portal "personal data" JSON API — `GET personal/frontend/data/items?type=personal_data` → find the entry with `key == "card.balance"` (id is a server-issued long hash, fetched dynamically; `net.balance` 网费 is available the same way) → `GET personal/frontend/data/detail?id=<id>` → `d.data.value`. Auth rides the shared `CASTGC` through the portal's own CAS entry `cas_login/1` (its redirect target consumes the ticket; pointing `service=` at the bare root does NOT work); that ticket-consuming hop is what mints `CK_LC`/`CK_VL`, and nothing re-issues them afterwards. History: the portal and ecard balance values were out of sync (portal read higher) until 2026-09, when the university fixed it — `EcardClient` (Jsoup-based scraper of the plain-HTTP `ecard.neu.edu.cn` self-service site, incl. the two same-name `.ASPXAUTSSM` Set-Cookie later-wins pitfall documented in `.har/ecardlogin.har`) was removed wholesale along with the Jsoup dependency and the settings source switcher; keep its `.har` captures as reference material
6. `HdrHelper` — Ultra HDR gainmap utility for the experimental HDR QR highlight: `isHdrSupported` (API 34+ and an HDR-capable display) gates the mode; `attachGainmap` mounts a gainmap on the QR bitmap (white/quiet-area modules get full gain, black modules zero) so only the QR exceeds SDR white
7. **Silent re-login** (`SilentLogin` ledger + `SilentRelogin` driver + `CasAuthClient` protocol + `CredentialStore`) — 解决"余额在每次登录约 2 小时后必然失效"。`CASTGC` 无法续期,唯一出路是再登录一次;本地存了账密就能无人完成。**它就是"自动续期",不是并列于登录的另一个功能**:与交互登录共用 `CasAuthClient` 与同一套成功判据,差别只在"旁边有没有人填验证码"。流程:`MainActivity.runSilentRelogin()` 开一个协程(返回 Boolean:false = 已有一发在跑,本次既不发请求也不会有任何回调,调用方得自己决定等还是降级,见 Activities 里 MainActivity 那条)→ `SilentRelogin.run()` 过 `SilentLogin.decide()` 拿到许可并 `claim()` 占住单飞位 → `CasAuthClient.loginSilently()` 自己取登录页、自己算 RSA、自己 POST 账密 → 拿到票就跟随到服务端消费 → 再用 `EcodeApiClient.hasAuthenticatedSession()` 做**真校验**(qr-code 200)才算成功。触点是 `QrFetchResult.AuthExpired` 与 `BalanceResult.SessionExpired`。三个结局各自收场:**`Success`** 补做原先失败的那件事(继续拉码 / 重查余额),二维码那边失败则 `degradeQrSession()`(只清 ecode 的 cookie,保留 CASTGC 与门户凭据);**`NeedSecondFactor(form)`** 先把界面降级,再**打开登录页的二次验证面板**,把那张已被服务端接受的表单交给它(`CasSecondFactorForm` 可序列化,随 Intent 过去)——用户只补一个验证码,不必让登录页把同一份账密再提交一遍;**`Rejected`** 打开登录页,账号预填、密码清空、说明"保存的密码已失效";无存账密/冷却中/熔断/网络异常则安静降级成空态(`Unavailable`/`Error`),因为"退回未登录"本身就是"该手动登录一次了"的信号
   `SilentLoginOutcome` 是 sealed(`Success`/`NeedSecondFactor(form)`/`Rejected`/`Unavailable`/`Error`)。护栏:单飞(`claim()` 带 90 s 自愈超时)、60 s 冷却(撞到二次验证拉长到 10 分钟,**`Success` 也上冷却**——防"假成功"变成死循环)、**连续两次 `Rejected` 熔断**——存错密码 + 自动重试是唯一可能把账号搞进风控的路径,所以只有 `Rejected` 计数(要二次验证、网络异常都不算)。这些护栏**只约束后台自动重试**;界面上的动作走的是"提交一份账密并当场看服务端怎么答",根本不经过 `decide()`,所以不需要也不可能被冷却挡住(2026-09-14 曾为此给 `decide()` 加过 `manual` 豁免参数,随调试入口一起删除)。熔断那一刻 `SilentRelogin` 会调 `CredentialStore.clearPassword()`:**只删密码、留账号名**,否则那个已知错误的密码会在每次打开登录页时被预填回去。静默路径**永不调用 `requestSmsCode`**,所以它不可能替用户发短信,也不可能替用户做图形验证码——它只会把人送到能填验证码的那一页。历史(同日上半场,已被上面这版取代):它最初是"不可见登录页 Activity + JS 注入调页面自己的 `login()`"实现的,并因此无限闪屏——(a) 成功判据 `url.contains("ecode.neu.edu.cn")` 对 CAS 登录 URL 恒真(它的 `service=` 参数只转义 `:` 和 `/`,主机名原样保留),页面一次都没提交就自报成功;(b) 整窗 `alpha=0` 不会让不透明窗口变透明,主界面每跳一次就黑一下。改原生后这两类问题从结构上消失:成功变成"换到票 + 真校验通过",没有窗口、没有 JS 注入。`WebLoginActivity` 的 host 判定(`isEcodeUrl`,按 `Uri.parse(url).host` 解析)仍是主机名比较,别退回子串匹配。凭据存在 `EncryptedSharedPreferences`(AndroidKeyStore 主密钥,`allowBackup=false`),**唯一的写入者是登录页**,并且只在服务端接受过这份账密之后才写,绝不从 CAS 页面抓取,也没有第二个录入口;交互登录两条路都会预填(原生表单直接填字段,`WebLoginActivity` 走 `prefillCredentials` 注入)以免校外还要手打账号

### 原生 CAS 客户端(`CasAuthClient` + `SilentRelogin`,2026-09-14)

应用自己的 CAS 登录实现:**不用 WebView,不用 JS 注入**,分步 API 让"静默"与"交互"共用同一段协议代码。

```kotlin
fetchLoginForm()                       // 取登录页 → lt / execution / action / 公钥;一上来就 302 = 本地 TGT 还活着
submitCredentials(form, user, pass)    // 提交账密 → Ticket(location) / SecondFactor(form) / BadCredentials(msg?) / Unclear
fetchCaptcha()                         // GET /tpass/code → image/jpeg 原样返回
requestSmsCode(form, captcha)          // POST /tpass/secondAuthCode {code, method} → {success, message}
submitSecondFactor(form, captcha, sms) // 隐藏字段原样重放,只覆盖 imgCode/scendAuthCode/method/_eventId
establishSession(entryUrl, host)       // 拿活着的 TGT 换票并跟随到服务端消费 → OK / NO_TGT / ELSEWHERE
consumeTicket(location, verify)        // 交互路径的收尾:消费 Ticket 的 Location,再过真校验 → Boolean
loginSilently(user, pass, verify)      // 静默全流程;撞到二次验证就把那张表单装进 NeedSecondFactor 交回界面,永不发短信
```

**谁调谁**(两条路共用协议,只是交互那条旁边有人填验证码):
- 静默:`SilentRelogin.run()` → `loginSilently()`
- 交互:`LoginActivity` → `fetchLoginForm()/submitCredentials()/[fetchCaptcha()+requestSmsCode()]/submitSecondFactor()` → `consumeTicket()`
- 交接:静默撞上二验时 `loginSilently()` 返回 `NeedSecondFactor(form)`,由 `MainActivity` 开 `LoginActivity.intentForSecondFactor(form)` 让交互那条接着走**同一张**表单——两条路在这里合流,而不是各走一遍

要点:

- **不缓存任何一次性 token**:`lt`/`execution` 每次加载现取;RSA 公钥优先从 `login_neu.js` 现场解析(校方换密钥时不会静默失效),解析不到才用内置常量。公钥方案与页面 jsencrypt 双向验证过(`RSA/ECB/PKCS1Padding`)
- **提交字段与顺序照抓包**:`rsa`/`ul`/`pl`/`lt`/`execution`/`_eventId=submit` + 三个恒为空的 `t_un`/`t_pd`/`t_c`。`pl` 传的是**长度**,密码只出现在 `rsaEncrypt` 的入参里,不进日志。这套字段在真机上跑过 10/10(demo/fingerprint-lab)
- 提交地址取自**页面自己的 `form#loginForm` action**(真实值是 `/tpass/login?service=…`,即 service 由页面携带),不硬编码;`ECODE_ENTRY` 只是入口与空 action 的兜底。选择器已按真实页面核实:`input#lt`、`input[name=execution]`
- 判定顺序:302 带 `ST-` → `Ticket`;200 含 `second_auth_form` → 二验页;200 含 `#loginForm` → 账密被拒(错误文案 `visibleErrorText()`:**先读 `#errormsghide`,再读可见的 `#errormsg`**——`#errormsg` 在干净页面上就带着一段 `display:none` 的占位文案「账号不存在！」,而真实文案由页面自己的 JS 从 `#errormsghide` 搬过去,详见 "CAS/CASTGC session lifetime" 里 `errorlogin.har` 那条);其余 → `Unclear`。登录页里 `second_auth_form`/`scendAuthCode`/`imgCode` 出现 0 次,所以字符串判定不会被惰性模板骗到
- **`Success` 的定义是"换到票 + `verify()` 通过"**,不是"cookie 里有东西"。静默路径的 verify 是 `EcodeApiClient.hasAuthenticatedSession()`(qr-code 200);上一版无限闪屏的根因正是拿本地 cookie 当成功
- 请求头统一走 `navHeaders()`(UA + `Accept-Language` + `Upgrade-Insecure-Requests` + `Sec-Fetch-*`,`document` 与 XHR 两套)。只求"像浏览器",不追求逐字节复刻 Chrome 的头顺序与 `sec-ch-ua`(OkHttp 做不到)
- 依赖:Jsoup 回到 `app` 依赖里(解析登录页/二验页,选择器是在真机验证过的;`minify` 关闭,约 +450 KB)。`AppHttp` 是全局共享的 OkHttp + `WebViewCookieJar`,主界面与登录页因此共用同一份会话。`UserAgent.adoptWebViewUserAgent()` 在 `MainActivity.onCreate` 就调一次——否则"进程起来直接静默重登"会用兜底 UA,与 WebView 不一致
- **仍是 WebView 的地方**:`WebLoginActivity`(登录页底部常驻的"网页登录(兼容模式)"入口)与 `WebViewCookieJar`(会话存储;换掉它要迁移已有会话,是独立的一步)。因为 UA 仍取自 WebView 提供方,`windowIsTranslucent` 那套窗口技巧已随静默模式一起删除——现在没有任何不可见界面

### Fingerprint lab (gitignored `demo/fingerprint-lab/`)

A standalone Android app (`com.neboer.fplab`, builds with its own wrapper: `cd demo/fingerprint-lab && ./gradlew assembleDebug`) built for one open question: is the second factor keyed on **IP**, on **device fingerprint**, or both. It replays the credential login over OkHttp with a *chosen* fingerprint and reports whether the server answered with a ticket or with the 2FA page. Reuses the RSA path already proven in `demo/src/main/.../CasAuthenticator.kt` (`RSA/ECB/PKCS1Padding` + SPKI + base64); that scheme was cross-verified against the page's own jsencrypt with `.har/_fixture/rsa_interop.js` + `RsaInteropCheck.java` (private key decrypts jsencrypt's ciphertext ⇒ same padding), and the parse selectors (`form#loginForm` / `input#lt` / `input[name=execution]`) were re-verified against the real captured login page. Why only the UA/Client-Hints are variable: the server gets **no** JS fingerprint (see above) and **no** device cookie, so the HTTP request is the entire surface — but TLS/JA3 is *not* variable from OkHttp, which is why the iOS/desktop profiles are marked `tlsCoherent = false` in the UI as known confounds.

## Conventions and gotchas
- The codebase is in Chinese: UI strings, comments, and log messages. New strings go in `res/values/strings.xml` (with `values-night` colors already handled by the DayNight theme). Keep new logs in Chinese to match
- Never log passwords — usernames may appear in debug logs, passwords never should
- Logging policy (agreed design, the old spec doc has been deleted): remove all `Log.d`, keep `Log.e` and minimal `Log.i`. The Material 3 UI part is applied (M3 DayNight theme, 东大蓝 `#003366` palette in `colors.xml` + `values-night/`), but the logging cleanup is **not** applied — `Log.d` remains pervasive and is the debugging breadcrumb trail for the auth flow
- When login breaks, suspect a server-side change at `pass.neu.edu.cn`/`ecode.neu.edu.cn` first — the code is a screen-scraper, not an API client
- **UI 版式约定**(跟着 `activity_settings.xml` 走,新页面照抄即可):页面 = `MaterialToolbar`(`ic_arrow_back` + `navigationIconTint=?attr/colorOnSurface` + `actionBarSize`)+ `ScrollView(padding=16dp, clipToPadding=false)`;内容一律装在 `MaterialCardView` 里(`cardBackgroundColor=?attr/colorSurfaceContainer`、`cardCornerRadius=16dp`、`cardElevation=1dp`、`strokeColor=?attr/colorOutlineVariant`、`strokeWidth=1dp`、卡间距 16dp),卡片内 `padding=16dp`;行间分隔用 1dp 的 `View` + `colorOutlineVariant`。字号只有四档:卡片标题 15sp 粗体、行标题 14sp 粗体、正文/按钮/下拉 13sp、说明与错误文案 12sp(`colorOnSurfaceVariant`,错误用 `colorError`)。**按钮只用两种样式**:主操作 `Widget.Material3.Button.TonalButton`、次要 `Widget.Material3.Button.TextButton`(别引 OutlinedButton 之类第三种);分区标 13sp 粗体 `colorPrimary`。凭据输入框一律 `importantForAutofill="no"`(这是应用自己要存的同一份凭据,不该被系统/第三方密码管理器顺走)
- Release build has minify disabled; all endpoints are HTTPS (the `usesCleartextTraffic` exemption was removed along with the plain-HTTP ecard site)
